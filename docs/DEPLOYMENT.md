# Развёртывание и серверные мощности

## 1. Замеры (8 ноября 2026)

Продакшен-сборка, один процесс Next.js, PostgreSQL на той же машине, 4 vCPU Intel Xeon 2.3 ГГц.
Нагрузка — `autocannon`, 20 одновременных подключений, 15 секунд на страницу, вошедший студент.

| Что | Результат |
|---|---|
| Страница входа | ~210 запросов/с, задержка ~95 мс |
| «Сегодня» (запросы к базе) | ~145 запросов/с, ~135 мс |
| «Заявки» (запросы к базе) | ~140 запросов/с, ~145 мс |
| Проверка пароля argon2id | ~10 мс; ~350 входов/с на 4 ядрах |
| Память Node.js без ограничения | 280 МБ в покое → ~790 МБ под нагрузкой |
| Память Node.js с `--max-old-space-size=512` | **~290 МБ** под той же нагрузкой, скорость та же (~140 запросов/с) |
| Память PostgreSQL | ~250 МБ |
| Размер базы с демо-данными | ~9 МБ |

Один процесс Node.js использует в основном **одно ядро**, поэтому ~140 запросов/с — это
производительность одного ядра. Масштабируется добавлением процессов/серверов: сессии хранятся
в базе, приложение не хранит состояние в памяти.

## 2. Сколько это пользователей

Студент за один визит открывает ~5 страниц. Утренний пик: допустим, 20 % студентов заходят за 10 минут.

| Студентов в вузе | Пиковая нагрузка | Хватит |
|---|---|---|
| Жюри конкурса (десятки человек) | < 1 запроса/с | 1 процесс, загрузка ~1 % |
| 5 000 | ~8 запросов/с | 1 процесс |
| 30 000 | ~50 запросов/с | 1 процесс на пределе комфорта → 2 процесса для запаса и отказоустойчивости |
| 100 000 | ~170 запросов/с | 3–4 процесса + отдельный сервер базы |

Это оценка по замерам на демо-данных; для настоящего вуза нужен нагрузочный тест на реальных объёмах.

## 3. Рекомендуемый сервер для конкурса

| Параметр | Минимум | Рекомендуется |
|---|---|---|
| vCPU | 1 | **2** |
| RAM | 2 ГБ + swap 2 ГБ | **4 ГБ** |
| Диск | 20 ГБ SSD | **30–40 ГБ NVMe** |
| ОС | Ubuntu 24.04 LTS | Ubuntu 24.04 LTS |
| Сеть | публичный IPv4 | публичный IPv4 |

Почему 4 ГБ, а не 2: сама работа укладывается в ~0,6 ГБ (приложение ~290 МБ с ограничением
`NODE_OPTIONS`, PostgreSQL ~250 МБ, Caddy ~30 МБ), но **сборка** Docker-образа (`next build`)
кратковременно требует 1,5–2 ГБ. С 2 ГБ сборка возможна только со swap.

Провайдеры с дата-центрами в России (доступ без VPN): Timeweb Cloud, Yandex Cloud, Selectel, VK Cloud.
Сервер нужен оплаченным **до 28 ноября** включительно.

## 4. Масштаб «настоящего вуза» (для описания проекта)

```
           ┌──────────── балансировщик (HTTPS) ────────────┐
           ▼                       ▼                        ▼
   приложение #1 (2 vCPU/2 ГБ)  приложение #2  …  приложение #N
           └───────────────┬───────────────────────────────┘
                           ▼
        управляемый PostgreSQL (2–4 vCPU, 8 ГБ) + реплика + бэкапы
```

- Приложение без состояния → добавляем копии под нагрузку.
- Управляемая база (Yandex Managed PostgreSQL и т. п.) — бэкапы и реплики «из коробки».
- Тяжёлая операция — только вход (argon2): ~350 входов/с на 4 ядрах с запасом покрывают пиковые утренние волны.

## 5. Шаги развёртывания (этап 6)

1. Арендовать VPS, установить Docker и Caddy.
2. `git clone`, создать `.env`: длинный случайный `POSTGRES_PASSWORD`, свой `DEMO_PASSWORD`.
3. `mkdir -m 700 secrets` — отдельная папка для логинов и паролей: контейнер импорта работает от root
   и получает на запись только её, а не весь проект.
4. `docker compose run --rm migrate` — таблицы, импорт `data/university` и демо-данные.
   Логины и пароли студентов появятся в `secrets/credentials.csv` на сервере (права 600) — не публикуйте его.
5. `docker compose up -d app` — приложение (слушает только `127.0.0.1:3000`).
6. Caddy: домен → `reverse_proxy 127.0.0.1:3000`, `header_up X-Real-IP {remote_host}`; HTTPS и HSTS.
7. Проверить с телефона через мобильный интернет без VPN, вписать ссылку и пароль в README.
8. Cron: ночное пересоздание демо-данных, ежедневный бэкап базы (`pg_dump`).

## 6. Обновление версии на сервере

```bash
git pull
docker compose build                 # ОБЯЗАТЕЛЬНО: run/up без --build берут старый образ
docker compose run --rm migrate      # миграции + импорт data/university + демо-данные
docker compose up -d app             # перед стартом сервис schema ещё раз применит миграции
docker compose logs app | head       # должно быть «✓ База на месте, миграции применены»
```

- **`docker compose build` после каждого `git pull`.** `docker compose run` и `up` без `--build`
  используют уже собранный образ. С ним `migrate` применит старый набор миграций, а приложение останется
  старой версией или запустится новое на необновлённой базе.
- **Сервис `schema`** (`npx prisma migrate deploy`) запускается перед `app` при каждом `docker compose up`.
  Новая версия не стартует на базе без новых колонок. Демо-данные он не трогает: их пересоздаёт `migrate`.
- **Проверка:** `curl -s https://<домен>/api/health`. Без входа отвечает `{"ok":true}` или код 503.
  Вошедшему сотруднику деканата показывает подробности: какие миграции не применены и версию сборки.
- После обновления откройте страницы заново. Сборка получает версию (`DEPLOYMENT_VERSION` →
  `deploymentId` в `next.config.ts`), поэтому вкладка, открытая на старой версии, при переходе
  перезагрузится сама и не будет слать серверу действия от старой сборки.

## 7. Если на сервере не сохраняются данные

Признак: страницы открываются, но кнопки «Сохранить», «Отправить» или смена статуса ничего не меняют.

1. **`docker compose logs app`**:
   - `⚠ В базе не применены миграции…` — выполните шаги раздела 6;
   - `[action:…]` — ошибка при сохранении: код и первая строка, без данных пользователей.
2. **Плашка «Страница загрузилась не полностью»** — браузер не получил файлы интерфейса.
   Браузер сам сообщает об этом серверу:
   `docker compose logs app | grep "\[client\]"` → `[client] script-error /_next/static/chunks/… на странице /staff`.
   Дальше проверьте сервер скриптом (с сервера или с любого компьютера):
   ```bash
   bash scripts/check-static.sh https://ваш-домен 20
   ```
   - **«Разных версий страницы: 2» или 404 у файлов** — отвечают два экземпляра кабинета разных версий.
     Возможные причины: старый контейнер (`docker ps`), процесс `npm start`/pm2 вне Docker (`sudo ss -ltnp | grep 3000`),
     два upstream в Caddy/nginx. Оставьте один, остальные остановите.
   - **Ответы 502 или 000** — приложение перезапускается: `docker inspect -f '{{.RestartCount}}' <контейнер app>`,
     `docker compose logs app`, `free -m` (не хватает памяти).
   - **Всё 200, а плашка есть** — проблема между браузером и сервером: кэширующий прокси/CDN, VPN, антивирус.
   При первом сбое загрузки страница один раз перезагружается сама, плашка — если сбой повторился.
   Подробнее о том, что означает плашка: браузер не получил
   файлы `/_next/static`. Обычно это старый процесс сервера после пересборки или обрыв соединения
   на прокси. Нажмите «Обновить страницу» и перезапустите приложение (`docker compose up -d app`).
   Без этих файлов работают смена статуса справки, новая заявка (выбор вида справки — CSS) и уведомления
   (кроме полей с подсказками «Группа» и «Преподаватель»): формы отправляются обычным способом (`action`).
   Подсказки при вводе (оценки, группы) требуют JavaScript.
3. **Форма показывает «база данных не обновлена…»** — примените миграции (раздел 6).
4. **Форма показывает «ошибка на сервере»** — подробности в `docker compose logs app`.

Как это проверено (17.11): standalone-сборка как в Dockerfile, запуск `node server.js` с переменными
из `docker-compose.yml`, Playwright.
- Смена статуса и уведомление записываются в базу и видны студенту — и с JavaScript,
  и при заблокированных `/_next/static/*.js`.
- На базе без двух последних миграций сервер при запуске пишет предупреждение,
  а `/api/health` отвечает 503.
