# Развёртывание и серверные мощности

## 1. Замеры (8 ноября 2026)

Продакшен-сборка, один процесс Next.js, PostgreSQL на той же машине, 4 vCPU Intel Xeon 2.3 ГГц.
Нагрузка — `autocannon`, 20 одновременных подключений, 15 секунд на страницу, вошедший студент.

| Что | Результат |
|---|---|
| Страница входа | ~210 запросов/с, задержка ~95 мс |
| «Сегодня» (запросы к базе) | ~145 запросов/с, ~135 мс |
| «Заявки» (запросы к базе) | ~140 запросов/с, ~145 мс |
| Проверка пароля argon2id | ~10 мс; ~350 входов/с на 4 ядрах |
| Память Node.js без ограничения | 280 МБ в покое → ~790 МБ под нагрузкой |
| Память Node.js с `--max-old-space-size=512` | **~290 МБ** под той же нагрузкой, скорость та же (~140 запросов/с) |
| Память PostgreSQL | ~250 МБ |
| Размер базы с демо-данными | ~9 МБ |

Один процесс Node.js использует в основном **одно ядро**, поэтому ~140 запросов/с — это
производительность одного ядра. Масштабируется добавлением процессов/серверов: сессии хранятся
в базе, приложение не хранит состояние в памяти.

## 2. Сколько это пользователей

Студент за один визит открывает ~5 страниц. Утренний пик: допустим, 20 % студентов заходят за 10 минут.

| Студентов в вузе | Пиковая нагрузка | Хватит |
|---|---|---|
| Жюри конкурса (десятки человек) | < 1 запроса/с | 1 процесс, загрузка ~1 % |
| 5 000 | ~8 запросов/с | 1 процесс |
| 30 000 | ~50 запросов/с | 1 процесс на пределе комфорта → 2 процесса для запаса и отказоустойчивости |
| 100 000 | ~170 запросов/с | 3–4 процесса + отдельный сервер базы |

Это оценка по замерам на демо-данных; для настоящего вуза нужен нагрузочный тест на реальных объёмах.

## 3. Рекомендуемый сервер для конкурса

| Параметр | Минимум | Рекомендуется |
|---|---|---|
| vCPU | 1 | **2** |
| RAM | 2 ГБ + swap 2 ГБ | **4 ГБ** |
| Диск | 20 ГБ SSD | **30–40 ГБ NVMe** |
| ОС | Ubuntu 24.04 LTS | Ubuntu 24.04 LTS |
| Сеть | публичный IPv4 | публичный IPv4 |

Почему 4 ГБ, а не 2: сама работа укладывается в ~0,6 ГБ (приложение ~290 МБ с ограничением
`NODE_OPTIONS`, PostgreSQL ~250 МБ, Caddy ~30 МБ), но **сборка** Docker-образа (`next build`)
кратковременно требует 1,5–2 ГБ. С 2 ГБ сборка возможна только со swap.

Провайдеры с дата-центрами в России (доступ без VPN): Timeweb Cloud, Yandex Cloud, Selectel, VK Cloud.
Сервер нужен оплаченным **до 28 ноября** включительно.

## 4. Масштаб «настоящего вуза» (для описания проекта)

```
           ┌──────────── балансировщик (HTTPS) ────────────┐
           ▼                       ▼                        ▼
   приложение #1 (2 vCPU/2 ГБ)  приложение #2  …  приложение #N
           └───────────────┬───────────────────────────────┘
                           ▼
        управляемый PostgreSQL (2–4 vCPU, 8 ГБ) + реплика + бэкапы
```

- Приложение без состояния → добавляем копии под нагрузку.
- Управляемая база (Yandex Managed PostgreSQL и т. п.) — бэкапы и реплики «из коробки».
- Тяжёлая операция — только вход (argon2): ~350 входов/с на 4 ядрах с запасом покрывают пиковые утренние волны.

## 5. Шаги развёртывания (этап 6)

1. Арендовать VPS, установить Docker и Caddy.
2. `git clone`, создать `.env`: длинный случайный `POSTGRES_PASSWORD`, свой `DEMO_PASSWORD`.
3. `mkdir -m 700 secrets` — отдельная папка для логинов и паролей: контейнер импорта работает от root
   и получает на запись только её, а не весь проект.
4. `docker compose run --rm migrate` — таблицы, импорт `data/university` и демо-данные.
   Логины и пароли студентов появятся в `secrets/credentials.csv` на сервере (права 600) — не публикуйте его.
5. `docker compose up -d app` — приложение (слушает только `127.0.0.1:3000`).
6. Caddy: домен → `reverse_proxy 127.0.0.1:3000`, `header_up X-Real-IP {remote_host}`; HTTPS и HSTS.
7. Проверить с телефона через мобильный интернет без VPN, вписать ссылку и пароль в README.
8. Cron: ежечасное восстановление демо-данных (§6), ежедневный бэкап базы (`pg_dump`).

## 6. Ежечасное восстановление демо-данных

Демо-аккаунты общие: жюри ставит оценки, подаёт заявки, обрабатывает их в деканате. Чтобы каждый следующий
посетитель видел витрину в исходном виде, сервер **каждый час** пересоздаёт демо-контент тем же seed, что
и при установке (`prisma/seed.ts`, ~15–20 с на основном наборе данных).

| Что | После восстановления |
|---|---|
| Оценки | исходные: 1-й срез у всех, 2-й — примерно у половины групп, 3-й срез и экзамены/зачёты пусты; FX Евы по «Ботанике» на месте; у группы Ларисы снова пуст 2-й срез «Зельеварения» |
| Заявки, объявления, уведомления, дедлайны | исходные (новые заявки и уведомления удаляются) |
| Аккаунты, пароли, сессии, данные вуза (студенты, расписание, карта) | **не меняются**: вошедшие посетители не выходят из кабинета |

Seed запускается в образе сборки (сервис `migrate` из `docker-compose.yml`: в нём Prisma CLI и `tsx`)
с другой командой — только seed, без миграций и импорта. Строка для `crontab -e` пользователя, который
запускает Docker (путь — папка клона на сервере):

```cron
# Каждый час в :00 — восстановить демо-данные. flock не даёт запуститься второй копии, если предыдущая не закончилась.
0 * * * * cd /opt/student_account && flock -n /tmp/demo-reseed.lock docker compose run --rm -T migrate npx prisma db seed >> /var/log/demo-reseed.log 2>&1
```

- `-T` — без терминала (в cron его нет); `--rm` — контейнер удаляется после запуска.
- Лог `/var/log/demo-reseed.log` должен быть доступен на запись этому пользователю
  (`sudo touch /var/log/demo-reseed.log && sudo chown $USER /var/log/demo-reseed.log`).
- Проверить вручную: `docker compose run --rm -T migrate npx prisma db seed` — в конце строка
  «Готово: оценок …, заявок …» и список тестовых аккаунтов.
- Во время пересоздания (секунды) страницы студентов могут на мгновение показать пустые оценки — данные
  удаляются и создаются заново. Поэтому в README у сценария для жюри указано, что данные возвращаются
  к исходным каждый час.

Вместо cron можно systemd-таймер (`/etc/systemd/system/demo-reseed.service` и `.timer`):

```ini
# demo-reseed.service
[Unit]
Description=Восстановление демо-данных кабинета
[Service]
Type=oneshot
WorkingDirectory=/opt/student_account
ExecStart=/usr/bin/docker compose run --rm -T migrate npx prisma db seed

# demo-reseed.timer
[Unit]
Description=Каждый час — восстановление демо-данных
[Timer]
OnCalendar=hourly
Persistent=true
[Install]
WantedBy=timers.target
```

Включить: `sudo systemctl daemon-reload && sudo systemctl enable --now demo-reseed.timer`;
журнал — `journalctl -u demo-reseed`. Таймер не запускает новую копию, пока предыдущая работает.
