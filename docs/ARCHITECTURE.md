# Архитектура

> Статус: **реализовано на этапе 2** (вход, сессии, разграничение доступа, заявки). Остальные разделы — этап 3.

## 1. Общая схема

```
Браузер (телефон / ПК)
      │  HTTPS, cookie сессии (httpOnly, Secure, SameSite=Lax)
      ▼
proxy.ts — «оптимистичная» проверка: нет cookie → /login (не защита, а скорость)
      │
      ▼
Next.js 16 (App Router)
  ├─ страницы и компоненты (React 19, Tailwind)
  ├─ layout разделов: requireStudent() / requireStaff()
  ├─ серверные действия (Server Actions) ← каждое само вызывает requireStudent() / requireStaff()
  └─ слой доступа к данным (lib/data/*) ← принимает контекст из сессии, всегда фильтр по владельцу
      │
      ▼
PostgreSQL (через Prisma)

Внешние сервисы (опционально): YandexGPT / GigaChat — только с сервера
```

**Масштабирование:** приложение не хранит состояние в памяти (сессии — в базе),
поэтому можно запускать несколько копий за балансировщиком. База — одна, с резервными копиями.

## 2. Стек

| Слой | Технология | Зачем |
|---|---|---|
| Фреймворк | Next.js 16 + TypeScript, React 19 | Интерфейс и сервер в одном проекте |
| UI | Tailwind CSS 4, компоненты по образцу shadcn/ui, Lucide, Inter | Быстрый современный интерфейс, лицензии MIT/ISC/OFL |
| База | PostgreSQL 16 | Надёжная реляционная база |
| ORM | Prisma 7 + драйвер `pg` | Типобезопасные запросы, понятная схема |
| Валидация | Zod | Проверка всех входных данных на сервере |
| Пароли | argon2 (argon2id) | Современное хеширование |
| Развёртывание | Docker Compose на VPS | Простой и переносимый деплой |
| Тесты | Vitest | Автотесты безопасности слоя данных |

### Принятые решения

| Решение | Почему |
|---|---|
| `cacheComponents` в Next.js 16 **выключен** | Почти каждая страница зависит от того, кто вошёл; кешировать на сервере нечего, а режим требует оборачивать каждое чтение сессии в `<Suspense>`. Без него код проще для людей и ИИ |
| Сессии в базе, а не JWT | Выход и смена пароля сразу делают старые сессии недействительными |
| Свои компоненты вместо `npx shadcn add` | Реестр shadcn недоступен из облачного окружения разработки; компоненты написаны по тому же образцу (лицензия MIT) |
| Шрифт через Fontsource, а не Google Fonts | Шрифт отдаётся с нашего сервера — не зависит от доступности Google из России |
| Клиент Prisma создаётся лениво (`lib/db.ts`) | Иначе `next build` падает без `DATABASE_URL` (найдено при сборке Docker-образа) |
| Расписание в seed — на весь осенний семестр | Жюри открывает кабинет в разные дни: пары, переносы и отмены есть на любой неделе |

## 3. Модель данных

Полная схема — `prisma/schema.prisma`. Кратко:

```
User            id, login, passwordHash, role (STUDENT | STAFF), createdAt
Session         id, userId, expiresAt                — хранится хеш токена
Faculty         id, name
Program         id, facultyId, name, code            — направление подготовки
Group           id, programId, name, course
Student         id, userId, groupId, lastName, firstName, middleName, recordBookNo
Staff           id, userId, facultyId, fullName, position
Teacher         id, fullName                         — вымышленные преподаватели
Subject         id, name
Lesson          id, groupId, subjectId, teacherId, type, room, startsAt, endsAt,
                status (NORMAL | MOVED | CANCELLED), originalStartsAt?, originalRoom?
Grade           id, studentId, subjectId, semester, kind (EXAM | CREDIT | COURSEWORK),
                value, date
Deadline        id, groupId, subjectId?, title, dueAt
RequestType     id, name, description, fields (JSON)
Request         id, studentId, typeId, payload (JSON),
                status (SUBMITTED | IN_PROGRESS | READY | ISSUED | REJECTED),
                staffComment?, createdAt, updatedAt
Announcement    id, authorId, title, body, audience (faculty / course / group), publishedAt
Notification    id, userId, type, title, body, link?, readAt?, createdAt
LoginAttempt    id, login, ip, success, createdAt   — для ограничения попыток
```

## 4. Безопасность

### 4.1 Вход (`lib/auth/`)
- Логин + пароль → проверка хеша **argon2id** (`password.ts`). Соль — своя у каждого хеша.
- Если логина нет, всё равно проверяется «пустой» хеш: по времени ответа нельзя понять, существует ли логин.
- Сообщение об ошибке одинаковое для неверного логина и неверного пароля.
- Ограничение (`rate-limit.ts`), неудачных попыток за 15 минут: 5 — с пары «логин + IP»,
  20 — с одного IP, 100 — на логин со всех IP. Высокий общий порог по логину — намеренно:
  иначе посторонний мог бы заблокировать чужой (демо-) аккаунт, просто вводя неверный пароль.
- Попытка записывается **до** проверки пароля, поэтому параллельные запросы не обходят лимит.
- IP берётся из `X-Real-IP` только при `TRUST_PROXY=1` (приложение за нашим Caddy/nginx,
  порт приложения открыт лишь на `127.0.0.1`). Иначе заголовок мог бы подделать любой клиент.
- При успехе (`session.ts`): 32 случайных байта → cookie `sid` (`httpOnly`, `Secure` в продакшене,
  `SameSite=Lax`, 7 дней). В базе хранится только **SHA-256 от токена**.
- Выход удаляет сессию из базы; старая cookie после этого не работает.
- Смена пароля закрывает все остальные сессии пользователя.
- Защита от CSRF: `SameSite=Lax` + встроенная проверка `Origin` у серверных действий Next.js.

### 4.2 Разграничение доступа (`lib/auth/guards.ts`, `lib/data/`)
- Роль проверяется на сервере для каждой страницы и действия (`requireStudent()`, `requireStaff()`).
  Они возвращают **контекст** (`StudentContext` / `StaffContext`) — брендированный тип,
  который нельзя случайно собрать вручную из id в адресе.
- **Студент:** все запросы к данным идут через функции из `lib/data/*`, которые принимают
  контекст и фильтруют по `studentId`. Id из адреса используется только вместе с фильтром владельца.
- Студент, открывший `/staff`, перенаправляется в свой кабинет; сотрудник на страницах студента — в свой.
- Если объект не принадлежит пользователю — ответ «Не найдено» (404), а не «Нет доступа»,
  чтобы не подтверждать существование чужой записи.
- **Сотрудник:** видит заявки и публикует объявления только в рамках своего факультета.

### 4.3 Демо-режим публичного стенда (`DEMO_MODE=1`)
- Демо-аккаунты общие для всех посетителей, поэтому смена пароля отключена (на сервере, а не только в интерфейсе).
- Не больше 10 активных заявок на студента и 5 новых в час — чтобы витрину нельзя было завалить спамом.
- План (этап 6): ночное пересоздание демо-данных по расписанию.

### 4.4 Секреты и данные
- Секреты (`DATABASE_URL`, `SESSION_SECRET`, ключи ИИ) — только в переменных окружения сервера.
- Никаких секретов в `NEXT_PUBLIC_*`, в коде и в репозитории. `.env` в `.gitignore`.
- Все входные данные валидируются Zod на сервере.
- Пароли и токены не пишутся в логи.
- Все данные — вымышленные, создаются seed-скриптом.

### 4.5 Проверка
- `tests/security.test.ts` — 14 автотестов: чужая заявка не открывается, сотрудник не меняет
  заявки чужого факультета, пароли — только хеши argon2id, блокировка после 5 ошибок входа,
  ошибки с одного адреса не блокируют аккаунт для других, лимит на подачу заявок.
- Аудит субагентом `security-reviewer` (8 ноября): утечек чужих данных и обхода ролей не найдено;
  найденные риски для демо-стенда исправлены, остальное — в `ROADMAP.md`, этапы 5–6.
- Сквозная проверка в браузере (Playwright): вход, подача заявки, подмена адреса → 404,
  смена статуса сотрудником → студент видит новый статус. Скриншоты — `docs/screenshots/2-*`.
- HTTP-заголовки: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`,
  `Permissions-Policy`; заголовок `X-Powered-By` отключён.

## 5. Структура проекта

```
app/
  (auth)/login/          страница входа
  (student)/             кабинет студента: today, requests, profile (+ schedule, grades, notifications — этап 3)
  (staff)/staff/         кабинет сотрудника: заявки факультета
lib/
  auth/                  сессии, хеширование, ограничение попыток, requireStudent / requireStaff
  data/                  доступ к данным с проверкой владельца
  validation/            схемы Zod
  generated/prisma/      клиент Prisma (генерируется, не коммитится)
components/              UI-компоненты
prisma/
  schema.prisma          схема базы
  migrations/            миграции
  seed.ts                вымышленные данные
tests/                   автотесты безопасности
proxy.ts                 быстрый редирект на /login без cookie
Dockerfile, docker-compose.yml
docs/                    документация проекта и для ИИ
```

## 6. Развёртывание

```
docker compose run --rm migrate   # миграции + демо-данные (образ сборки с Prisma CLI)
docker compose up -d app          # приложение (автономный сервер Next.js) + PostgreSQL
```

- Образ приложения ~90 МБ (сжатый): только собранный сервер, запуск от непривилегированного пользователя.
- База доступна только с самого сервера (`127.0.0.1:5432`).
- Перед приложением на сервере — nginx/Caddy с HTTPS (этап 6).
