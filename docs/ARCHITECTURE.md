# Архитектура

> Статус: **реализовано на этапе 2** (вход, сессии, разграничение доступа, заявки).
> Этап 3: данные вуза из заменяемых файлов (`data/university/`), импорт, слой данных расписания;
> успеваемость — роль преподавателя, назначения, оценки по срезам (`docs/specs/grades.md`); успеваемость факультета
> для деканата (`docs/specs/dean-grades.md`).

## 1. Общая схема

```
Браузер (телефон / ПК)
      │  HTTPS, cookie сессии (httpOnly, Secure, SameSite=Lax)
      ▼
proxy.ts — «оптимистичная» проверка: нет cookie → /login (не защита, а скорость)
      │
      ▼
Next.js 16 (App Router)
  ├─ страницы и компоненты (React 19, Tailwind)
  ├─ каждая страница: requireStudent() / requireStaff() / requireTeacher(); общие разделы (расписание, карта) — requireUser()
  ├─ серверные действия (Server Actions) ← каждое само вызывает requireStudent() / requireStaff() / requireTeacher()
  ├─ API (app/api/*) ← getUserContext(): без сессии — 401, а не редирект
  └─ слой доступа к данным (lib/data/*) ← принимает контекст из сессии, всегда фильтр по владельцу
      │
      ▼
PostgreSQL (через Prisma)

Внешние сервисы (опционально): YandexGPT / GigaChat — только с сервера
```

**Масштабирование:** сессии и все данные — в базе, поэтому можно запускать несколько копий за балансировщиком.
База — одна, с резервными копиями. Единственное состояние в памяти процесса — счётчик частоты сохранений
оценок (§3.2): при нескольких копиях он считается в каждой отдельно (для демо-стенда с одной копией этого достаточно).

## 2. Стек

| Слой | Технология | Зачем |
|---|---|---|
| Фреймворк | Next.js 16 + TypeScript, React 19 | Интерфейс и сервер в одном проекте |
| UI | Tailwind CSS 4, компоненты по образцу shadcn/ui, Lucide, Inter | Быстрый современный интерфейс, лицензии MIT/ISC/OFL |
| База | PostgreSQL 16 | Надёжная реляционная база |
| ORM | Prisma 7 + драйвер `pg` | Типобезопасные запросы, понятная схема |
| Валидация | Zod | Проверка всех входных данных на сервере |
| Пароли | argon2 (argon2id) | Современное хеширование |
| Развёртывание | Docker Compose на VPS | Простой и переносимый деплой |
| Тесты | Vitest | Автотесты безопасности слоя данных |

### Принятые решения

| Решение | Почему |
|---|---|
| `cacheComponents` в Next.js 16 **выключен** | Почти каждая страница зависит от того, кто вошёл; кешировать на сервере нечего, а режим требует оборачивать каждое чтение сессии в `<Suspense>`. Без него код проще для людей и ИИ |
| Сессии в базе, а не JWT | Выход и смена пароля сразу делают старые сессии недействительными |
| Свои компоненты вместо `npx shadcn add` | Реестр shadcn недоступен из облачного окружения разработки; компоненты написаны по тому же образцу (лицензия MIT) |
| Шрифт через Fontsource, а не Google Fonts | Шрифт отдаётся с нашего сервера — не зависит от доступности Google из России |
| Клиент Prisma создаётся лениво (`lib/db.ts`) | Иначе `next build` падает без `DATABASE_URL` (найдено при сборке Docker-образа) |
| Данные вуза — в заменяемых файлах, а не в seed | Кабинет можно перенести на другой вуз, заменив три файла; код не знает названий факультетов и групп |
| Импорт: сначала проверка всех файлов, потом одна транзакция | Ошибка в строке 20 000 не оставит базу «наполовину» загруженной |
| Лекция потока — одно занятие и связи с группами (`LessonGroup`) | Нет дублей, перенос лекции меняется в одном месте; дата продублирована в связи ради индекса «группа + даты» |
| Расписание за весь семестр и сессию | Жюри открывает кабинет в разные дни: пары, переносы и отмены есть на любой неделе |

## 3. Модель данных

Полная схема — `prisma/schema.prisma`. Кратко:

```
User            id, login, passwordHash, role (STUDENT | STAFF | TEACHER), isDemo, createdAt
Session         id, tokenHash (SHA-256 токена), userId, expiresAt, createdAt
LoginAttempt    id, login, ip, success, createdAt   — для ограничения попыток

── из students.csv ──
Faculty         id, code («ГР»), name, sortOrder (порядок в файле)
Program         id, facultyId, name                  — направление подготовки
Group           id, name, kind (ACADEMIC | LANGUAGE | OTHER), course?, facultyId?,
                parentId? (языковая группа → академическая), oid?
Student         id, externalId («ID студента»), userId, ФИО, email, recordBookNo,
                course, facultyId, programId, academicGroupId
StudentGroup    studentId, groupId, position (1/2) — языковые группы студента
Staff           id, userId, facultyId, fullName, position — по одному на факультет

── из schedule.csv и campus-map.json (расписание заменяется целиком) ──
Teacher         id, oid (lecturerOid), shortName, fullName, rank?, email?, userId? (1:1 User с ролью TEACHER)
TeachingAssignment  id, teacherId, disciplineId, groupId, finalKind? (EXAM | CREDIT), finalDate?
                — кто ставит оценки; заполняет импорт: «Семинар»/«Практическое занятие» группы без REPLACED;
                  уникально (teacherId, disciplineId, groupId); id сохраняются при повторном импорте
Building        id, key (id на карте), name, abbr?, address?, floors, wings?, maxRoom?, scheme?, onMap
Room            id, number («4144», «Манеж-1»), buildingId?, type?, capacity?, floor?, wing?, purpose?,
                bookable, onMap
Discipline      id, name, oid?
Lesson          id, oid (lessonOid), date, startTime, endTime («HH:MM» по Москве), startsAt, endsAt (UTC, задел),
                pairStart?, pairEnd?, disciplineId, kind («Лекция»…), teacherId?, roomId?, buildingId?,
                stream?, subGroup?, note?, url?, urlDescription?, status (NORMAL | MOVED | CANCELLED | REPLACED)
LessonGroup     lessonId, groupId, date — лекция потока = одно занятие + несколько групп
                индексы: LessonGroup(groupId, date), Lesson(teacherId, date)

── демо-контент (prisma/seed.ts) и действия пользователей ──
Grade           id, studentId, disciplineId, semester (семестр студента), kind (CHECKPOINT | EXAM | CREDIT),
                checkpoint (1–3 у среза, 0 у экзамена/зачёта), points? (0–100), passed? (зачёт),
                gradedByTeacherId? (SetNull), createdAt, updatedAt
                — уникально (studentId, disciplineId, semester, kind, checkpoint); CHECK в базе: баллы 0–100,
                  форма записи соответствует виду
Deadline        id, groupId, disciplineId?, title, dueAt
RequestType     id, code, name, description, etaDays
Request         id, studentId, typeId, payload (JSON),
                status (SUBMITTED | IN_PROGRESS | READY | ISSUED | REJECTED),
                staffComment?, createdAt, updatedAt
Announcement    id, authorId, title, body, facultyId? / course? / groupId? (аудитория), publishedAt
Notification    id, userId, type, title, body, link?, readAt?, createdAt
```

- **Карта кампуса** (`/map`) читает `campus-map.json` напрямую (`lib/campus-map/load.ts`) при каждом запросе —
  файл можно заменить без пересборки. Поля карты в `Building`/`Room` (этажи, крылья, вместимость, тип) —
  копия для будущего API и проверок; расписание берёт из базы только номер, этаж, название и адрес корпуса.
- **`Lesson.startsAt/endsAt`** — задел: импорт их заполняет, но сейчас никто не читает; время пары
  считается из `date` + `startTime`/`endTime` (`lib/moscow-time.ts`).

### 3.1 Импорт данных вуза (`npm run data:import`)

Код — `lib/university-data/` (тестируется без базы), команда — `scripts/import-university-data.ts`,
формат файлов — [`data/university/README.md`](../data/university/README.md).

```
students.csv ─┐
schedule.csv ─┼─► validate.ts: разбор CSV (BOM, «;»/«,», кавычки) + Zod по каждой строке
campus-map.json┘     карта — ТОЙ ЖЕ схемой, что и страница /map (lib/campus-map/schema.ts)
                     + перекрёстные проверки (группы студентов есть в расписании, уникальность…)
                     │ ошибки → «файл, строка N: колонка «…» — …», выход ≠ 0, база не тронута
                     ▼
                 import.ts: хеши паролей (вне транзакции) → ОДНА транзакция:
                   факультеты/направления/группы — upsert по коду/названию (id сохраняются)
                   дисциплины, преподаватели, корпуса, аудитории — по ключу; занятия — заново (createMany пачками)
                   студенты — по «ID студента» (заявки, оценки, пароли сохраняются), лишние — удаляются
                   деканаты — dekanat.<код латиницей>; тестовые аккаунты — пароль DEMO_PASSWORD
                     ▼
                 credentials.csv (вне git): логины и пароли новых и тестовых аккаунтов
```

- Основной набор (990 студентов, 23,5 тыс. строк расписания) загружается за ~10–15 с.
- `npm run db:seed` добавляет демо-контент поверх импорта и берёт факультеты, группы и дисциплины
  из базы — работает с любыми заменёнными файлами.

### 3.2 Успеваемость (`lib/data/grades.ts`, `lib/grades/`)

- Шкала ECTS, средние, цвета букв — `lib/grades/scale.ts`; текущий семестр (осень 2026/27, номер по курсу
  `2 × (курс − 1) + 1`) и сроки срезов — `lib/grades/term.ts`. Оба модуля без серверного кода.
- Студент: `getMyGrades(ctx, semester?)` — только `ctx.studentId`; дисциплины — всё, что есть в расписании его
  групп; итоговый контроль и преподаватели семинаров — из `TeachingAssignment`; прошлые семестры — пусто.
  Расчёт (средний по дисциплине, итоговый балл, долги, ближайший экзамен) — чистая `buildSemesterGrades`: её же
  вызывает деканат, поэтому цифры у студента и в деканате не расходятся. `loadStudentGrades(studentId)` — внутренняя
  функция слоя данных: её зовут только `getMyGrades` (id из сессии) и деканат (студент своего факультета).
  `getMyGradesDigest(ctx)` — кратко для «Сегодня»: итоговый балл (то же правило) и последние оценки.
- **Долг** (`hasFailing` в `lib/grades/stats.ts`, одно правило для сводки, карточки дисциплины и «Сегодня»):
  FX/F за срез, пока итоговый контроль не сдан, или проваленный итоговый контроль (экзамен ниже 60, «не зачтено»).
  Сданный экзамен (≥ 60) или «зачтено» гасит FX/F за срезы. `summary.failing` и `failingDisciplines` — число
  **дисциплин** с непогашенным долгом. FX — «можно пересдать», F — «нужно повторить курс».
- Преподаватель: `getMyAssignments(ctx)`, `getJournal(ctx, assignmentId)` — только назначения `ctx.teacherId`
  (чужое → null → 404). Студенты группы: академическая — `Student.academicGroupId`, языковая — `StudentGroup`.
- `saveGrades(ctx, input)` (действие `saveGradesAction`): ограничение частоты сохранений на преподавателя →
  Zod → своё назначение → каждый студент в группе назначения → экзамен/зачёт совпадает с `finalKind`;
  любая ошибка — ничего не сохраняется. Затем одна транзакция (advisory-блокировка по дисциплине, одна выборка
  имеющихся оценок, изменения и уведомления пачками; `timeout` 15 с). Ответ (`SaveGradesResult`) различает
  выставленные и стёртые оценки (`saved` / `cleared`) — журнал пишет «Сохранено: N» / «Стёрто: M»; стёртая оценка
  уведомления не создаёт. Лимит: 60 сохранений и 1000 оценок за 10 минут на преподавателя
  (`lib/auth/action-limit.ts`, в памяти одного процесса). Демо-режим ставить оценки не мешает.
- **Одновременная правка** (две вкладки, два семинариста группы): с каждой оценкой журнал отправляет значение,
  которое видел (`expected`); если в базе уже другое — не сохраняется вся пачка, у поля ошибка «Оценку уже
  поставили: …», в ответе свежие строки журнала. При возврате на вкладку без черновиков журнал подтягивает
  свежие данные. Несохранённые оценки журнала хранятся черновиком в `sessionStorage` (по назначению) и
  восстанавливаются после «Назад» с плашкой и кнопкой «Отменить».
- Изменённая оценка → запись `Notification` типа `GRADE` студенту («Новая оценка: …», ссылка на `/grades`).
  Ленты уведомлений в интерфейсе пока нет — записи в базе — задел под неё; студент видит новую оценку
  в «Оценках» и в блоке «Оценки» на «Сегодня».
- Demo: seed ставит 1-й срез всем и 2-й — примерно половине пар, 3-й срез и итоговые оценки — пусто; баллы
  в основном 60–100 без всплесков на границах, изредка FX. Тестовые преподаватели (`isDemo`) выбираются
  импортом из семинаристов групп тестовых студентов (`TEST_TEACHER_LOGINS` — явно).

### 3.2.1 Успеваемость для деканата (`lib/data/dean-grades.ts`, `lib/grades/course-stats.ts`)

- Только чтение, все функции принимают `StaffContext`, фильтр — `ctx.facultyId` из сессии (никогда из адреса):
  `getFacultyCourses`, `getCourseOverview(ctx, course?)` (неизвестный курс → первый курс факультета),
  `getFacultyGroupGrades(ctx, groupId)` (только академическая группа своего факультета),
  `getFacultyStudentGrades(ctx, recordBookNo, semester?)` → тот же `MyGrades`, что у студента,
  `isFacultyGroup` / `isFacultyStudent` (лёгкие проверки для layout), `searchFacultyStudents(ctx, q)`.
  Чужое, несуществующее или мусор → `null` / `false` → 404.
- Курс и группа читаются пачкой, без запроса на студента: студенты → пары «группа × дисциплина» из расписания одним
  `SELECT DISTINCT` (`LessonGroup` ⨝ `Lesson`) → назначения → оценки; для каждого студента — `buildSemesterGrades`.
  Замер (11 ноября, prod, 2 курс Слизерина — 60 студентов × 9 дисциплин): страница обзора ~150 мс, группы ~140 мс,
  студента ~105 мс, поиск ~55 мс.
- Сводка курса/группы (`cohortSummary`): средний — «среднее из средних» итоговых баллов студентов; распределение
  по букве итогового балла; студенты с долгом (`hasFailing` — то же правило, что у студента); заполнение идущего среза
  (после срока 3-го — 3-й): выставлено из «студент × его дисциплина». «Заполнение журналов» — по каждому назначению
  (дисциплина × группа × преподаватель): сколько студентов группы получили оценку за срез.
- Таблица группы: колонки — дисциплины академической группы; дисциплины языковых групп — колонки «1-й язык»,
  «2-й язык» (по `StudentGroup.position`: у соседей это разные языки).
- Поиск: зачётка — точное совпадение без учёта регистра (`exact` → сразу страница студента), ФИО — до 3 слов, каждое —
  часть фамилии, имени, отчества или зачётки; запрос до 64 символов, до 10 подсказок, знаки процента, подчёркивания и обратной косой черты экранируются.
  API `/api/staff/students/search`: без входа — 401, не деканат — 403 (`getStaffContext`), ответ — ФИО, зачётка,
  группа, курс (без id, логина, почты), `Cache-Control: private, no-store`. Без JavaScript форма уходит на
  `/staff/grades?q=…`, страница делает то же на сервере.

### 3.3 Слой данных расписания (`lib/data/schedule.ts`)

- Личное расписание — `getMyScheduleForDate(ctx, date?)`, `getMyScheduleForRange(ctx, from, to)`:
  группы студента (академическая + языковые) берутся **по `ctx.studentId` из сессии**; занятия
  соседних языковых групп не попадают.
- Открытое расписание вуза для любого вошедшего (`requireUser()` → `UserContext`): `listFaculties`,
  `searchScheduleTargets` (группы и преподаватели, **без студентов**), `getGroupSchedule`, `getTeacherSchedule`.
- «Сегодня» — по Москве (`lib/moscow-time.ts`); результат — плоские объекты (даты `YYYY-MM-DD`, время `HH:MM`).
- Период не длиннее 190 дней; неверные даты → `ScheduleRangeError` (общая `checkRange`).
- Заглушки «Перенесено на …» на исходной дате — `lib/data/schedule-moves.ts`: те же правила и помощники
  (`myGroupIds`, `checkRange`) из `lib/data/schedule.ts`.

## 4. Безопасность

### 4.1 Вход (`lib/auth/`)
- Логин + пароль → проверка хеша **argon2id** (`password.ts`). Соль — своя у каждого хеша.
- Если логина нет, всё равно проверяется «пустой» хеш: по времени ответа нельзя понять, существует ли логин.
- Сообщение об ошибке одинаковое для неверного логина и неверного пароля.
- Ограничение (`rate-limit.ts`), неудачных попыток за 15 минут: 5 — с пары «логин + IP»,
  20 — с одного IP, 100 — на логин со всех IP. Высокий общий порог по логину — намеренно:
  иначе посторонний мог бы заблокировать чужой (демо-) аккаунт, просто вводя неверный пароль.
- Попытка записывается **до** проверки пароля, поэтому параллельные запросы не обходят лимит.
- IP берётся из `X-Real-IP` только при `TRUST_PROXY=1` (приложение за нашим Caddy/nginx,
  порт приложения открыт лишь на `127.0.0.1`). Иначе заголовок мог бы подделать любой клиент.
- При успехе (`session.ts`): 32 случайных байта → cookie `sid` (`httpOnly`, `Secure` в продакшене,
  `SameSite=Lax`, 7 дней). В базе хранится только **SHA-256 от токена**.
- Выход удаляет сессию из базы; старая cookie после этого не работает.
- Смена пароля закрывает все остальные сессии пользователя.
- Защита от CSRF: `SameSite=Lax` + встроенная проверка `Origin` у серверных действий Next.js.
  Исключение — только через переменную `SERVER_ACTIONS_ALLOWED_ORIGINS` (задаётся лишь в GitHub Codespaces,
  где прокси подменяет заголовок `Origin` на `localhost:3000`). На боевом сервере переменная не задаётся.

### 4.2 Разграничение доступа (`lib/auth/guards.ts`, `lib/data/`)
- Роль проверяется на сервере для каждой страницы и действия (`requireStudent()`, `requireStaff()`, `requireTeacher()`).
  Они возвращают **контекст** (`StudentContext` / `StaffContext` / `TeacherContext`) — брендированный тип,
  который нельзя случайно собрать вручную из id в адресе.
- Общие для всех ролей разделы (расписание группы/преподавателя, карта) — `requireUser()` → `UserContext`
  (любой вошедший). Обработчики `app/api/*` вызывают `getUserContext()`: без сессии — ответ 401, а не редирект.
  Поиск расписания (`/api/schedule/search`) возвращает только группы и преподавателей, без студентов.
- **Студент:** все запросы к данным идут через функции из `lib/data/*`, которые принимают
  контекст и фильтруют по `studentId`. Id из адреса используется только вместе с фильтром владельца.
- Пользователь на странице чужой роли перенаправляется в свой кабинет (`HOME[role]`: `/today`, `/staff`, `/journal`).
- **Преподаватель:** видит студентов и оценки только групп из своих назначений (`TeachingAssignment`);
  сохранение проверяется на сервере (назначение, членство студента, вид итоговой оценки, баллы — целое 0–100).
- Если объект не принадлежит пользователю — ответ «Не найдено» (404), а не «Нет доступа»,
  чтобы не подтверждать существование чужой записи. У страниц с id в адресе (`/journal/[assignmentId]`,
  `/requests/[id]`) принадлежность проверяет ещё и `layout.tsx` сегмента: он выполняется до `loading.tsx`,
  поэтому чужой или мусорный id получает настоящий HTTP-статус 404, а не 200 со страницей «не найдено».
  Страница проверяет сама ещё раз (двойной рубеж).
- **Сотрудник:** видит заявки и публикует объявления только в рамках своего факультета. «Успеваемость» — оценки
  всех студентов **своего** факультета, только чтение (`lib/data/dean-grades.ts`, фильтр `ctx.facultyId`).
  Группа и студент из адреса (`/staff/grades/group/[groupId]`, `/staff/grades/student/[recordBookNo]`) проверяются
  в `layout.tsx` сегмента до `loading.tsx` → чужой факультет — настоящий HTTP 404; страница проверяет ещё раз.
  Поэтому у `staff/` и `staff/grades/` нет своих `loading.tsx`: они лежат в группах `(requests)` и `(overview)`.
  Студент и преподаватель на `/staff/*` перенаправляются в свой кабинет (`requireStaff`), API поиска студента
  отвечает им 403.

### 4.3 Демо-режим публичного стенда (`DEMO_MODE=1`)
- Демо-аккаунты общие для всех посетителей, поэтому смена пароля отключена (на сервере, а не только в интерфейсе).
- Тестовым аккаунтам (флаг `User.isDemo` в базе) пароль нельзя сменить и **без** `DEMO_MODE`: проверяют
  серверное действие и слой данных (`lib/data/account.ts`), профиль показывает объяснение вместо формы.
- Студент, убранный из тестовых при импорте, получает новый случайный пароль (демо-пароль знают все), его сессии закрываются.
- Не больше 10 активных заявок на студента и 5 новых в час — чтобы витрину нельзя было завалить спамом.
- Сохранение оценок ограничено по частоте на преподавателя (счётчик в памяти процесса): демо-аккаунт
  преподавателя нельзя «сломать» сотнями сохранений и уведомлений. Ставить оценки демо-режим не мешает.
- **Демо-данные восстанавливаются каждый час** (`npm run db:seed` по расписанию на сервере,
  [`DEPLOYMENT.md`](DEPLOYMENT.md#6-ежечасное-восстановление-демо-данных)): заявки, **оценки**, объявления,
  уведомления и дедлайны возвращаются к исходным — оценки, которые поставило жюри, живут до ближайшего часа.
  Аккаунты, пароли и сессии seed не трогает.

### 4.4 Секреты и данные
- Секреты (`DATABASE_URL`, `POSTGRES_PASSWORD`, `DEMO_PASSWORD`, в будущем — ключи ИИ) — только в переменных окружения
  сервера. Отдельного секрета для сессий нет: токен случайный, в базе — его SHA-256.
- Никаких секретов в `NEXT_PUBLIC_*`, в коде и в репозитории. `.env` в `.gitignore`.
- Все входные данные валидируются Zod на сервере.
- Пароли и токены не пишутся в логи.
- Все данные — вымышленные: вуз — из файлов `data/university/`, демо-контент — seed-скриптом.
- Пароли, выданные импортом, существуют в открытом виде только в `credentials.csv` (в `.gitignore`
  и `.dockerignore`, права 600); в консоль и логи не выводятся. В Docker контейнер импорта пишет только
  в `./secrets` (`secrets/credentials.csv`), а не во весь проект. Значения, похожие на формулы
  (`= + - @` в начале), записываются с апострофом. Оборванный импорт: `credentials.csv.tmp` при следующем
  запуске объединяется с основным файлом (только пароли, подходящие к хешам в базе).
- Тот же «ID студента» с другим логином или ФИО — сессии аккаунта закрываются, в отчёте импорта предупреждение.
- Файлы вуза — недоверенные данные: размер до 50 МБ (`campus-map.json` — до 5 МБ), поля расписания до 300 символов (ссылка — до 2048),
  ФИО — только буквы, пробел, дефис, апостроф, точка. Из `campus-map.json` в браузер уходят только известные поля.
- Ссылки на онлайн-занятия из файлов принимаются только `http(s)://` — `javascript:` не попадёт в кнопку;
  при отдаче и отрисовке ссылка ещё раз проверяется `safeExternalUrl` (`lib/safe-url.ts`).
- Поиск расписания экранирует `%`, `_` и `\` (Prisma передаёт `contains` в ILIKE как есть).

## 6. Развёртывание

```
docker compose run --rm migrate   # миграции + импорт data/university + демо-данные (образ сборки с Prisma CLI)
docker compose up -d app          # приложение (автономный сервер Next.js) + PostgreSQL
```

- Образ приложения ~90 МБ (сжатый): только собранный сервер, запуск от непривилегированного пользователя.
- База доступна только с самого сервера (`127.0.0.1:5432`).
- Перед приложением на сервере — nginx/Caddy с HTTPS (этап 6).
