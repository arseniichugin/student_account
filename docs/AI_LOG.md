какие промпты сработали, где ИИ ошибался и как это исправлялось.

## Записи

### 2026-11-17 · Этап 6 · Форма заявки: не выбирался вид справки
**Инструмент:** Claude Code (облачная сессия), Playwright
**Задача:** на сервере статусы и уведомления заработали (через запасной путь без JS), но в форме новой заявки «кнопки выбора
вида справки не работают».
**Промпт:** «Изменение статуса справок и уведомления работают. Однако не работает форма отправки справок: кнопки выбора вида
справки не работают. слей с main»
**Результат:** ИИ понял, что на сервере пользователя по-прежнему не загружаются файлы интерфейса: формы работают только потому,
что получили запасной путь без JavaScript. Подсветка выбранной карточки справки зависела от состояния React, а отправки
без JS не было. Теперь выбор — обычные радиокнопки с подсветкой через CSS (`:has(:checked)`) и отправка `action`.
Так же переделаны «таблетки» формы уведомлений и кнопки оценки 5–1; поля «Курс» и «Дата и время» показываются через CSS.
Проверено на standalone-сборке при заблокированных `/_next/static/*.js`: заявка выбранного вида и уведомление курсу записаны в базу.
**Ошибки ИИ и исправления:** при прошлых доработках для работы без JS ИИ поправил отправку форм, но не проверил элементы выбора
внутри них — пользователь нашёл это на сервере.
**Сделано вручную:** проверка на сервере, слияние.

### 2026-11-17 · Этап 6 · Плашка «Страница загрузилась не полностью» на сервере
**Инструмент:** Claude Code (облачная сессия), Playwright
**Задача:** на сервере статус справки по-прежнему не меняется, плашка о незагрузившемся интерфейсе появляется периодически.
**Промпт:** «нет, статус справки все равно не обновляется. Периодически появляется: Страница загрузилась не полностью…»
**Результат:** «периодически» означает, что файлы `/_next/static` отдаются нестабильно. Типичные причины: два экземпляра
кабинета разных версий за прокси, перезапуски контейнера, кэш прокси. Доступа к серверу у ИИ нет, поэтому добавлены
средства, которые показывают причину на месте:
- браузер сообщает серверу, какой файл не загрузился (`POST /api/client-log` → `[client] …` в логе);
- скрипт `scripts/check-static.sh` 20 раз запрашивает страницу и её файлы и находит 404 и разные версии;
- при первом сбое страница один раз перезагружается сама, плашка появляется через 15 с, а не через 8 (не пугает на медленном соединении).
Проверено Playwright на standalone-сборке: блокировка всех файлов, одиночный сбой, строки в логе сервера.
Формы, работающие без JS (предыдущая запись), исправляют симптом, но попадут на сервер только после слияния ветки.
**Ошибки ИИ и исправления:** первая версия плашки срабатывала через 8 с без гидратации и могла пугать на медленном соединении.
**Сделано вручную:** проверка на сервере.

### 2026-11-17 · Этап 6 · На сервере не сохранялись статусы справок и уведомления
**Инструмент:** Claude Code (облачная сессия); субагент-исполнитель (тестовые аккаунты преподавателей); `security-reviewer`; Playwright
**Задача:** после выкладки на сервер смена статуса справки и уведомления не доходили до базы и не появлялись у студента;
проверить запись в БД, исправить; сделать тестовые аккаунты преподавателей.
**Промпт:** «в новой версии следующие действия не приводят к изменениям: изменение статуса справки в ЛК деканата не меняет
его в БД (предположение) и в ЛК студента ничего не отображается. Аналогично с уведомлениями. Проверь, делаются ли записи
в БД во время работы сервера. Исправь эти ошибки. Запусти субагента чтобы тот сделал тестовые аккаунты для преподавателей»
**Результат:**
- ИИ собрал слитый `main` так же, как Dockerfile (standalone), запустил с переменными из `docker-compose.yml` на копии базы
  и проверил записи прямо в PostgreSQL: на обновлённой базе статус и уведомления сохраняются и видны студенту.
- Проверил две гипотезы на воспроизведениях: (а) база без новых миграций — падает весь кабинет, это не совпало
  с описанием; (б) не загружаются файлы `/_next/static` (старый процесс сервера после пересборки, старая вкладка,
  обрыв на прокси) — страницы видны, вход работает, а кнопки, работающие через JS, молча ничего не делают. Совпало.
- Исправления:
  - формы смены статуса, уведомлений и оценок сохраняют данные и без JS (атрибут `action`);
  - `deploymentId`: вкладка старой версии перезагружается сама;
  - ошибки сохранения видны пользователю и пишутся в лог (`runAction`);
  - `/api/health` и сообщение при запуске показывают, применены ли миграции;
  - сервис `schema` в Docker применяет миграции перед стартом приложения;
  - инструкция по обновлению в `DEPLOYMENT.md`.
- Субагент сделал по тестовому преподавателю на каждого тестового студента (`v.chernykh`, `g.suvorova`, `s.romanov`)
  и переменную `TEST_TEACHER_LOGINS`.
- Тестов 159 — зелёные.
**Ошибки ИИ и исправления:** `security-reviewer`: `/api/health` без входа показывал версию и имена миграций — теперь только
`ok`; лог ошибок писал исключение целиком (там бывают данные людей) — теперь код и первая строка; удаление оценки молча
проглатывало ошибку — исправлено. ИИ не смог проверить сам сервер пользователя (нет доступа) — причина установлена по
воспроизведению, точную картину покажут `docker compose logs app` и `/api/health`.
**Сделано вручную:** выкладка на сервер, описание проблемы.

### 2026-11-17 · Этап 3 · Кабинет преподавателя, кружки «новое», диагностика форм
**Инструмент:** Claude Code (облачная сессия); субагент-исполнитель (распределение групп); `security-reviewer`, `ui-reviewer`; Playwright
**Задача:** (1) в Codespace у пользователя не работали форма оценок (не подтягивался студент, поля неактивны) и смена
статуса справки; (2) кружки с числом новых оценок и изменённых заявок; (3) кабинет преподавателя: распределить группы
(одна группа — один преподаватель на год), расписание, оценки и рассылка только своим группам, уведомления от деканата
(«всем преподавателям», «преподавателю …»), без справок; документация.
**Промпт:** «в форме для выставления оценок проблемы: не подтягивается студент при вводе, поля предмет, Оценка и дата
занятия не активны. Плюс еще не работает изменение статуса справки. Проверь. Еще добавь на иконки Оценки и Заявки кружки…»
и «создай также личный кабинет для учителей. Запусти субагента, который распределит группы по учителям…»
**Результат:**
- Диагностика: у ИИ в облаке всё работало (проверено Playwright по адресу 127.0.0.1). ИИ заметил, что все симптомы —
  ровно то, что ломается без JavaScript (вход работает и без JS, а подсказки, кнопки и выбор — нет), и связал это
  с обрывами соединения при пробросе порта, которые были у пользователя раньше. Добавлено предупреждение
  «страница загрузилась не полностью» с кнопкой «Обновить», `start.sh` теперь останавливает старый сервер до сборки.
- Кружки: `Student.marksSeenAt`, `Request.statusSeen`; подсветка «Новая» / «Статус изменился».
- Субагент написал `tools/teacher-assignment/assign_teachers.py` и переписал `schedule.csv`: пар «группа + предмет»
  с несколькими преподавателями было 295 → 0 (+19 исключений: параллельные практики потока), накладок 5 → 0.
  ИИ перепроверил результат своим независимым подсчётом.
- Роль `TEACHER`: аккаунты при импорте, «Моё расписание», `/teacher/marks`, `/teacher/notifications`, общий раздел
  `/notifications`, у деканата — «Всем преподавателям» и «Преподавателю…». Документация — `docs/TEACHERS.md`.
  Тесты — `tests/teachers.test.ts`, всего 158 — зелёные.
**Ошибки ИИ и исправления:**
- первая версия импорта давала всем 106 преподавателям общий опубликованный пароль — `security-reviewer` указал,
  что так можно войти под любым преподавателем (логин = часть почты). Теперь демо-пароль у одного тестового,
  остальным — случайные; бывшему тестовому пароль меняется, сессии закрываются;
- деканат мог удалить оценку преподавателя, не было лимита ввода оценок — исправлено (лимит 300 в час, на демо-стенде 60);
- `ui-reviewer`: метка «Новая» исчезала сразу (страница сама отмечала просмотр и перерисовывалась) — метка теперь
  запоминает значение при первом показе; кружок был красным (цвет тревоги) — стал `--primary`; предупреждение о JS
  закрывало шапку и было непонятно на телефоне — переделано;
- seed ставил оценки за сегодняшние пары, которые ещё не закончились (время «выставления» в будущем) — исправлено;
- `prisma migrate dev` отказался работать неинтерактивно — миграция собрана через `prisma migrate diff` и применена `migrate deploy`.
**Сделано вручную:** постановка задачи, проверка в Codespace.

### 2026-11-17 · Этап 3 · Уведомления: события деканата
**Инструмент:** Claude Code (облачная сессия); субагенты `security-reviewer` и `ui-reviewer`; Playwright

  проваливалось, ссылка «Уведомления» на компьютере была вне меню и без подсветки, изменения расписания не выделены
  цветом — исправлено;
- тест падал, если перед ним тем же деканатом отправляли события (лимит демо-режима) — тест сделан независимым.
**Сделано вручную:** постановка задачи.

### 2026-11-17 · Этап 3 · Оценки на занятиях: база, вкладка студента, ввод деканатом

Тесты: `tests/marks.test.ts` + проверки в тестах импорта и меню, всего 136 — зелёные.
**Ошибки ИИ и исправления:**
- импорт пересоздаёт все занятия — с обычной связью «оценка → занятие» (каскад) оценки исчезали бы при каждом импорте;

- `ui-reviewer`: при 6 пунктах обрезалось «Расписание», удаление оценки без подтверждения, слабый контраст столбцов,
  двойная подсказка у недоступного поля — исправлено;
- `security-reviewer` (критичных нет): оценку можно было поставить за сегодняшнюю пару, которая ещё не началась;
  повторная привязка после импорта не сверяла дату, предмет и группу; нет CHECK в базе — исправлено;
- тест `marks.test` полагался на демо-оценки, которые удаляют тесты импорта, и падал при втором прогоне — переписан

   (Node.js + PostgreSQL, установка, демо-данные, сборка, автозапуск, инструкция).
3. Проверить в настоящем Codespaces ИИ не может, поэтому **воспроизвёл его у себя**: та же конфигурация
   в Docker на чистой копии проекта — установка с нуля прошла.
4. ИИ заранее знал о подводном камне: прокси Codespaces подменяет адрес, и Next.js отклоняет формы
   как CSRF. Нашёл в документации Next.js 16 настройку `serverActions.allowedOrigins` и включил её
   только через переменную окружения (на боевом сервере защита строгая).

**Ошибки ИИ и исправления:**

| Что пошло не так | Как обнаружено | Исправление |
|---|---|---|
| Первый тест «вход через адрес Codespaces» прошёл и **без** настройки — то есть ничего не доказывал | ИИ сделал контрольный прогон «должно упасть» — а оно не упало | Браузер не даёт подменить заголовок `Origin`. Написан мини-прокси, имитирующий Codespaces, + подмена DNS в браузере. Теперь: без настройки — отказ («origin does not match»), с настройкой — вход работает |

5. Вопрос пользователя «придётся ли создавать Codespace заново после каждого исправления?» вскрыл
   недочёт: при повторном открытии запустилась бы **старая** версия. ИИ добавил автообновление
   (`git pull` + установка/миграции/демо-данные/сборка — только то, что изменилось) и проверил
   полный цикл в Docker: создание — 57 с; открытие без изменений — 3 с; открытие после нового коммита —
   версия обновилась.

6. **Проверка пользователем в настоящем Codespace** нашла две проблемы, которых не было в имитации:
   - ошибка 502 при открытии — помогло переподключение порта во вкладке PORTS (вероятно, вкладка
     открылась раньше, чем запустился сервер);
   - вход падал с «This page couldn't load». ИИ воспроизвёл ровно этот экран у себя: переменная
     `SERVER_ACTIONS_ALLOWED_ORIGINS` не дошла до сервера. В имитации ИИ передавал её контейнеру
     вручную, а в Codespaces с Docker Compose `containerEnv` не сработал — **имитация не повторила
     настоящий путь передачи настройки**. Исправлено: переменная задаётся в `start.sh` (при запуске)
     и в `docker-compose.yml`. Проверено, что её достаточно передать при запуске, без пересборки.
   - при повторном запуске `start.sh` — «EADDRINUSE: порт 3000 занят»: старый сервер продолжал работать
     в другом терминале. `start.sh` теперь сам останавливает прежний сервер. Первая версия шаблона
     поиска процесса в тесте «убила» сам тестовый скрипт — шаблон сужен до процессов Next.js.
   - вход всё равно падал. По логу сервера со скриншота пользователя выяснилось, что **гипотеза ИИ
     была неверной**: Codespaces подменяет не адрес сервера, а заголовок `Origin` (на `localhost:3000`).
     ИИ строил имитацию по описанию проблемы из памяти, а не по реальным данным. Имитация
     переделана по реальному логу — ошибка воспроизведена дословно; исправление (разрешить и
     `localhost:3000`) проверено на ней.
   - и снова не помогло: в контейнере осталось старое значение переменной из прошлой версии, а скрипт
     задавал её только «если не задана». Ошибка была видна в строке запуска «Формы принимаются с адресов:
     *.app.github.dev» — диагностическая строка, добавленная шагом раньше, окупилась сразу.
     Теперь значение задаётся всегда; проверено именно с заранее заданным старым значением.

**Вывод для процесса:** имитацию внешней среды строить по реальным логам, а не по памяти; и у каждого теста должен быть контрольный прогон, который обязан упасть, —
